# Temporal

## Activity retries and timeouts

**Read 2026-09-29**, for `procedureActivity`'s handling of refused starts (OpenSpec `temporary-start-refusals`). What a caller sets is in the activity's doc comment; these are the facts it rests on.

- **`maximumAttempts` counts attempts, and is unlimited by default.** "Setting the value to 1 means a single execution attempt and no retries"; "The default is unlimited." The default policy retries with a 1 s initial interval, backoff 2.0, capped at 100 s, "until it either succeeds or is canceled" ([retry policies](https://docs.temporal.io/encyclopedia/retry-policies)).
- **`nextRetryDelay` replaces the policy's interval for that retry**, and "your retries will still cap out under the Retry Policy's Maximum Attempts, as well as overall timeouts. For an Activity, its Schedule-to-Close Timeout applies" ([retry policies](https://docs.temporal.io/encyclopedia/retry-policies)).
- **`scheduleToCloseTimeout` spans every attempt and the delays between them**: "from when the first Activity Task is scheduled to when the last Activity Task … reaches a Closed status". Its default is unlimited ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **A delay that would pass `scheduleToCloseTimeout` ends the activity at once, not at the deadline, and not as a `TimeoutFailure`.** The documentation is silent here; the server's source is not. `nextBackoffInterval` answers `RETRY_STATE_TIMEOUT` when `now + interval` is past the expiration ([`retry.go`](https://github.com/temporalio/temporal/blob/main/service/history/workflow/retry.go)), and the failed-task handler then records the activity's own failure with that retry state ([`respondactivitytaskfailed/api.go`](https://github.com/temporalio/temporal/blob/main/service/history/api/respondactivitytaskfailed/api.go)). A workflow sees an `ActivityFailure` whose cause is the `ApplicationFailure` the activity threw.
- **`startToCloseTimeout` applies per attempt**: "applied to each Activity Task Execution within an Activity Execution" ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **Cancellation reaches an activity only through its heartbeat**: "Activities that don't Heartbeat can't receive a Cancellation" ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **Workflow code cannot change an activity's options once it is scheduled**: the TypeScript workflow API fixes them in `proxyActivities` and offers no call to change them. **An operator can**, from outside: `temporal activity update-options` changes a running or scheduled activity's timeouts and retry policy, marked "an experimental feature" ([CLI](https://docs.temporal.io/cli/activity)).

## Workers, the dev server and Temporal Cloud

**Read 2026-09-30**, for the workflow project (OpenSpec `temporal-workflow-project`, [ADR 0016](../../adr/0016-a-workflow-project-is-a-generated-caller.md)). Versions: `@temporalio/*` 1.24.0 (2026-09-15, engines `node >= 20.3.0`); the Temporal CLI 1.9.1 (2026-09-14).

- **The dev server is enough locally.** `temporal server start-dev` serves the Web UI on the gRPC port plus 1000 (8233), persists to SQLite with `--db-filename` ("By default, Workflow Executions are lost when the server process dies"), creates namespaces with `--namespace` ("The 'default' Namespace is always created automatically"), registers `--search-attribute`s, binds `--ip` (default `localhost`) and has `--headless`; it "is not intended for production use" ([CLI](https://docs.temporal.io/cli/server)). SQLite 3.31+ supports advanced visibility, custom search attributes included ([visibility](https://docs.temporal.io/self-hosted-guide/visibility)), so Elasticsearch adds nothing a local run relies on. `temporalio/docker-compose` is archived. Installed by `brew install temporal` or a download from `temporal.download`; no npm package ships the CLI.
- **`TestWorkflowEnvironment.createLocal()` runs that same CLI**, downloaded and cached under `$TMPDIR` by default, or the one at `server.executable: { type: 'existing-path', path }` (`@temporalio/testing` 1.24.0 source). `createTimeSkipping()` runs the Java test server instead, which "does not support full capabilities of the regular Temporal Server" and on ARM needs Rosetta.
- **Node and Bun.** The SDK's CI tests Node 20 and 24 and Bun, Bun allowed to fail; Bun support is "experimental" (1.15.0), without source maps or stack-trace queries and with "no guarantee workflows between Node and Bun are valid" (sdk-typescript #1906). **Observed 2026-09-30**: on Node 26.8.2 the native core bridge loads and `createLocal()` starts the brew CLI (1.6.2, server 1.30.2) — outside the tested range, so a workflow project's own `test` runs it on every build.
- **The workflow bundle.** `bundleWorkflowCode` is webpack with swc; a prebuilt `workflowBundle` "is the recommended way to deploy Workers to production", and the `@temporalio/worker` that bundles must be "the exact same version" that runs it. `workflowsPath` bundles at `Worker.create`, for development (`@temporalio/worker` 1.24.0 `worker-options.ts`). Alpine and musl are unsupported.
- **Temporal Cloud with an API key**: `NativeConnection.connect({ address, apiKey })`, TLS on whenever `apiKey` is set (`@temporalio/common` `tls-config.ts`). The namespace endpoint `<namespace>.<account>.tmprl.cloud:7233` is the recommended one ([API keys](https://docs.temporal.io/cloud/api-keys)); the namespace must allow API-key authentication. Workers need only outbound gRPC on 7233; PrivateLink is optional ([connectivity](https://docs.temporal.io/cloud/connectivity)).
- **`@temporalio/envconfig` is GA** (1.15.0). `loadClientConnectConfig(options)` returns `{ connectionOptions, namespace }` from `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_API_KEY`, `TEMPORAL_TLS*`, `TEMPORAL_GRPC_META_*` and a TOML profile, the environment taking precedence. Two silent paths: a missing profile file is ignored, and an unset address is not checked. `disableFile: true` skips the file.
- **A worker's shutdown cancels its activities without a requested cancel.** `Worker.shutdown()` stops polling and, after `shutdownGraceTime` (default 0), cancels running activities with the reason `WORKER_SHUTDOWN`; an activity that throws the `CancelledFailure` is marked failed so the server retries it sooner. The lang-side shutdown path passes cancellation details from a proto that may be absent, so `cancellationDetails().workerShutdown` is not reliable there — only `cancelRequested` identifies a cancel the workflow asked for (`@temporalio/worker` 1.24.0 `worker.js`). The runtime's default `shutdownSignals` are `SIGINT`, `SIGTERM`, `SIGQUIT`, `SIGUSR2`.
- **ECS**: the default 30 s before `SIGKILL` is raised with the task definition's `stopTimeout` (Fargate's maximum is 120 s) ([Temporal on ECS](https://temporal.io/blog/deploying-temporal-workers-to-amazon-ecs)). The official reference is Terraform; there is no official CDK construct.
- **Worker Versioning is GA** (2026-03-30), but the Worker Controller that runs versions side by side is Kubernetes-only (§ODO011). Scaling signals are schedule-to-start latency and `worker_task_slots_available`, not CPU alone ([worker best practices](https://docs.temporal.io/best-practices/worker)).

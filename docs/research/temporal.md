# Temporal — activity retries and timeouts

**Read 2026-09-29**, for `procedureActivity`'s handling of refused starts (OpenSpec `temporary-start-refusals`). What a caller sets is in the activity's doc comment; these are the facts it rests on.

- **`maximumAttempts` counts attempts, and is unlimited by default.** "Setting the value to 1 means a single execution attempt and no retries"; "The default is unlimited." The default policy retries with a 1 s initial interval, backoff 2.0, capped at 100 s, "until it either succeeds or is canceled" ([retry policies](https://docs.temporal.io/encyclopedia/retry-policies)).
- **`nextRetryDelay` replaces the policy's interval for that retry**, and "your retries will still cap out under the Retry Policy's Maximum Attempts, as well as overall timeouts. For an Activity, its Schedule-to-Close Timeout applies" ([retry policies](https://docs.temporal.io/encyclopedia/retry-policies)).
- **`scheduleToCloseTimeout` spans every attempt and the delays between them**: "from when the first Activity Task is scheduled to when the last Activity Task … reaches a Closed status". Its default is unlimited ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **A delay that would pass `scheduleToCloseTimeout` ends the activity at once, not at the deadline, and not as a `TimeoutFailure`.** The documentation is silent here; the server's source is not. `nextBackoffInterval` answers `RETRY_STATE_TIMEOUT` when `now + interval` is past the expiration ([`retry.go`](https://github.com/temporalio/temporal/blob/main/service/history/workflow/retry.go)), and the failed-task handler then records the activity's own failure with that retry state ([`respondactivitytaskfailed/api.go`](https://github.com/temporalio/temporal/blob/main/service/history/api/respondactivitytaskfailed/api.go)). A workflow sees an `ActivityFailure` whose cause is the `ApplicationFailure` the activity threw.
- **`startToCloseTimeout` applies per attempt**: "applied to each Activity Task Execution within an Activity Execution" ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **Cancellation reaches an activity only through its heartbeat**: "Activities that don't Heartbeat can't receive a Cancellation" ([activity timeouts](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).
- **Workflow code cannot change an activity's options once it is scheduled**: the TypeScript workflow API fixes them in `proxyActivities` and offers no call to change them. **An operator can**, from outside: `temporal activity update-options` changes a running or scheduled activity's timeouts and retry policy, marked "an experimental feature" ([CLI](https://docs.temporal.io/cli/activity)).

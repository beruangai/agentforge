# Proposal

## Why

A consumer adopting AgentForge wires an agentic project by hand today: layer manifests and their locks, a three-level image chain, Dockerfiles, a server and task entry per agent, a construct per agent — and then connects its callers to agents whose AgentCore runtime names are generated at deploy. `examples/agentic-project` shows the shape but not the connection: its e2e starts each container and builds each agent's client by hand, and nothing tells a deployed caller which runtime serves which agent. It also runs on scripts and paths inside this repository that no consumer has, and nothing keeps a consumer's copy of that wiring correct as AgentForge changes (§REQ709).

[ADR 0010](../../../adr/0010-agentforge-is-consumed-as-an-nx-plugin.md) settles that AgentForge is consumed as an Nx plugin: agents nest in a project, the project is what a caller connects to, and an ownership contract decides what an upgrade touches. §ODO003 has waited for a hand-built example to design from, and that example now exists. StrategyFoundry is generated by the plugin (A7), so the plugin comes first.

## What Changes

- **The package becomes an Nx plugin.** `@beruangai/agentforge` carries generators, executors and a sync generator beside its entry points, bundled and published with it.
- **An agentic project is a project of agent components.** Each agent is recorded once as a component in the project's metadata, in `@aws/nx-plugin`'s component form; every piece of wiring that spans the project's agents is derived from those records — the build targets, the project client, the project construct.
- **Generators**, following `@aws/nx-plugin`'s conventions and composing its public generators rather than copying them:
  - `init` — what `nx add @beruangai/agentforge` runs: the workspace's dependencies and the sync generator's attachment.
  - `agentic-project` — a project holding the shared **base layer**: the capabilities every agent in the project shares — modules, MCP servers, options, skills, `CLAUDE.md`, dependencies.
  - `agent` — an agent component: its contract with one stub procedure, its procedures, its task and server entries, its `.claude/`, its image, its construct.
- **One client per agentic project**, generated and maintained, typed by every agent's contract and built from a mapping of agent to runtime: local containers resolved by name, AgentCore runtimes resolved from the runtime configuration the deployment registers, or transports the caller supplies. The Temporal activity takes any of its procedures unchanged.
- **Constructs, not infrastructure.** Each agent gets a construct in `@aws/nx-plugin`'s shared constructs project (`packages/common/constructs`) that deploys it as its own AgentCore runtime and registers it in `@aws/nx-plugin`'s runtime configuration (AppConfig); the project gets a construct wrapping its agents and granting a caller invocation of exactly them (§REQ708). The consumer's infra project declares them where it wants them; the plugin never edits a stack or its checks.
- **Client support in AgentForge**: a transport to a local container found by name, and AgentCore transports resolved from a deployment's runtime configuration.
- **Executors** replace the scripts the examples reach into this repository for: `lock` (a layer's lock of the container workspace), `image` (the AgentForge image, the agentic image, each agent image) and `serve` (an agent's image running locally beside DynamoDB Local).
- **What updates maintain, and what the consumer owns.** Every artifact a generator creates is either **maintained** — kept by sync and by regeneration to what the installed AgentForge version generates from the project's components — or **scaffolded** — written once and never touched again. A consumer **detaches** a maintained artifact by naming it in the project's metadata, and owns it from then on.
- **Each layer's folder is named for what it becomes in the image**: `base/agentic/` is `/workspace/agentic`, `agents/<agent>/agent/` is `/workspace/agentic/agent` — the source, contract included, not only what is copied. Replaces `files/`.
- **The container workspace's root lock ships in the package**, so a consumer builds the AgentForge image from what it installed, at the versions AgentForge was tested with.
- **A golden example, `packages/examples/golden-kata`, generated by the plugin.** A short, bounded, non-looping pair in the shape consumers build: an agent produces an artifact in a filesystem of its own, a second agent assesses it, each returning a typed result.
  - `base` — shared conventions (`CLAUDE.md`, a skill), shared options, shared schemas, and a shared MCP server whose tool runs a kata's cases against a solution deterministically.
  - `writer` — writes a small kata: its description, cases, and a reference solution it checks with the shared tool.
  - `grader` — grades a kata against a fixed rubric, each criterion scored with its reasoning.
  - Every run is bounded (a time budget, capped turns) and isolated: each task works in a scratch filesystem of its own, removed when the task ends.
  - Its infra, `packages/examples/golden-kata-infra`, is created with `@aws/nx-plugin`'s `ts#infra` and declares the project construct by hand, as a consumer would. Its end-to-end tests are bespoke to this repository: locally through the project client over `serve`, and on AgentCore through the same client resolved from the runtime configuration.
- **`examples/` leaves the workspace**, so the plugin can iterate without keeping the hand-built examples building and passing as their shape drifts. It stays on disk as reference until the plugin works; then `hello-agent`'s end-to-end coverage is ported into the golden example or `hello-agent` is reattached.

## Capabilities

### New Capabilities

- `plugin-agentic-project`: adding AgentForge to a workspace; generating an agentic project and its base layer; building the AgentForge and agentic images from what the workspace installed; the ownership contract — maintained, scaffolded, detached — and sync keeping maintained artifacts current.
- `plugin-agentic-agent`: generating an agent as a component of its project; building its image and serving it locally.
- `plugin-agentic-connection`: connecting a project's agents to callers and infrastructure — the project client, each agent's construct registered in the runtime configuration, the project construct and the grant it gives a caller.

### Modified Capabilities

- `client-task-calls`: a transport to a local container found by name, and transports resolved from a deployment's runtime configuration.

## Requirements

- **Serves:** §REQ709 (adopting and upgrading without hand-wiring, the consumer's own work never overwritten), §REQ701 (one client whether the runtimes are local containers or AgentCore, chosen when it is built), §REQ707 (each agent resolvable by its name in the project), §REQ708 (a caller granted exactly the project's agents), §REQ704 (a consumer extends an image in the base layer, or by detaching an agent's `Dockerfile`), §REQ101 (every procedure of every agent is typed by the contract the caller imports, with no per-procedure wiring), §REQ203 (a session composes exactly the layers its project declares).
- **Resolves** §ODO003, changing two of its parts: the procedure generator is dropped — a contract and its procedures are the consumer's once stubbed — and so is the generated infra project with its `synth`, `checkov` and seeded `checkov.yml`, since infrastructure is the consumer's ([ADR 0010](../../../adr/0010-agentforge-is-consumed-as-an-nx-plugin.md)).
- **Leaves unmet here**, each a later change of A5: generating the Temporal worker and workflow layer and connecting a caller project to an agentic project; S3 filesystems in the golden example.

## Interfaces

- **The package's published surface grows**: generators, executors and a sync generator; the container workspace's root manifest and lock as published files; in `/client`, `localContainerTransport` and `agentCoreTransportsFromRuntimeConfig`. The generators belong in the one package because they are versioned with the code they wire; the transports belong in `/client` because finding a runtime is the caller's side of the boundary.
- No change to the A2A wire, the task-process IPC, `/agent`, `/server` or `/infra`.
- [ADR 0008](../../../adr/0008-code-ships-in-the-image.md) and [ADR 0010](../../../adr/0010-agentforge-is-consumed-as-an-nx-plugin.md) are amended in place with this change's decisions, before implementation; §REQ709 is added to `REQUIREMENTS.md`.
- Resolving a deployment's own agents by name from the map it registers is resolution by name (§REQ707), not agent discovery, which stays out of scope; SOLUTION_SPACE and ARCHITECTURE §10 say so.

## Impact

- **Lands after `move-package-to-libs`**: this change is written against `libs/agentforge`.
- **Package:** a `plugin/` concept folder; `nx`, `@nx/devkit`, `@aws/nx-plugin` and `@aws-sdk/client-appconfigdata` become optional peers; the bundle carries the plugin's manifests, schemas and templates.
- **Workspace:** `packages/common/*` (from `@aws/nx-plugin`) and `packages/examples/*` join the workspace; `examples/*` leaves it and `.nxignore` hides it. `hello-agent`'s deployed stack stays, unmanaged, until its fate is decided.
- **Credentials:** local serving reads the subscription token from `.env.serve.local`, which the operator creates. The test role gains AppConfig read in `us-east-2` (`integ/aws/test-role-permissions-policy.json`), applied by the operator.
- **Verification:** `golden-kata`'s local and AgentCore e2e replace `agentic-project`'s, and exercise a scratch filesystem end to end. The Temporal activity and S3 filesystems have no end-to-end run in the workspace until their iterations; `integ` still covers their slices.
- **Docs:** ARCHITECTURE §7–§10, ROADMAP A5, SOLUTION_SPACE, CLAUDE.md and `.claude/rules/testing.md` (examples in `packages/examples/`), GLOSSARY — added: base layer, agentic image, agent image, AgentForge image, agent component, project client, project construct, maintained, scaffolded, detached; retired: base image (as a term), agentic layer, agentic base image — §ODO003 resolved, `docs/research/aws-nx-plugin.md` rewritten with dated evidence.

## Success criteria

- `golden-kata` is generated by the plugin's generators from an empty directory, then its domain code written by hand; re-running every generator in the synced workspace leaves no diff.
- Its end-to-end test passes locally against a real model through the project client, each agent in its own container — A5's exit.
- Deployed, the same test passes through the same client resolved from the runtime configuration.
- The project construct grants a caller role invocation of exactly the project's agents and read of the stage's runtime configuration, asserted on the synthesised template.
- `nx sync` reports drift in a maintained artifact and restores it, and leaves a detached one untouched.
- No target in `golden-kata` names a path inside `libs/agentforge` or `dist/`.

## Pending for the next changes of A5

Recorded here so they are not lost; each lands on `golden-kata` first.

- **The Temporal layer** (next): a generator for a caller project — a worker and its workflows — and a connection generator joining it to an agentic project: the dependency on the project's client, the worker's grant from the project construct, and the runtime configuration's application id reaching the worker. `golden-kata` gains a write → grade workflow. The caller role `golden-kata-infra` grants today becomes the worker's.
- **Looping and longer workflows** as further examples when needed: a revise loop resuming the writer's session with the grader's reasoning, capped in rounds.
- **S3 filesystems in `golden-kata`**: the scratch filesystem becomes an S3 filesystem shared by both agents, one prefix per workflow run, so a run's files never meet another's and the grader reads the writer's files rather than receiving them.
- **Switchable surfaces in `golden-kata-infra`**: the example's own stack, not anything generated, enables layers by flag — the Temporal worker, S3 filesystems — so one example tests several surfaces.
- **`hello-agent`'s coverage**: port its end-to-end checks — the Temporal activity, `LOST` and a retry attaching, cross-container resume, S3 filesystems on AgentCore — into the golden example, or reattach `hello-agent`; then delete `examples/agentic-project`, and `hello-agent` with its deployed stack if it is not reattached.
- **An e2e stub** a generated project may start from, showing how to wire its tests; the tests stay the consumer's.
- **After A8 publishes the package**: `nx migrate` migrations, and an e2e of the plugin against a fresh workspace installing the published version.

## Non-goals

- The Temporal layer, S3 filesystems in the golden example, looping examples — later changes of A5.
- A procedure generator: once stubbed, a contract and its procedures are the consumer's; AgentForge changes how procedures run through what it maintains — the entries and the middleware — never through them.
- Generating or editing an infra project, a stack or its checks.
- Generating end-to-end tests.
- A client or a grant per agent for callers: the project is the unit a caller connects to.
- Regenerating or refactoring `hello-agent`.

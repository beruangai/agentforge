# Design

## Context

See proposal.md — Why. What holds today:

- **The task's metadata.** `taskMetadata(envelope, admission)` (`server/runtime/executor.ts`) writes into the A2A task's metadata: `procedure`, `contractHash`, `idempotencyKey`, `runtimeSessionId`, `attempt`, `priorAttempt`, `continuityKey`, `metadata`, `tags` and `runs`. Two places call it:
  - the executor, at admission;
  - the gateway (`server/runtime/gateway.ts`), building the task it stores `TASK_STATE_REJECTED` when a start's envelope exceeds the input cap.

  The client's `WireTaskSchema` reads `attempt` and `runs` from it into `TaskView`.
- **The server's config** (`server/runtime/server.ts`): `ServerConfig` holds each value, and `ServerOptions` is its `taskEntry` and `requiredSecrets` plus a `Partial` of the rest. Each value comes from `startServer`'s options or the environment, and a missing one throws (`required(…)`). `agentName` and `tableName` are read this way. `ExecutorConfig` and `GatewayConfig` are built from it.
- **Where a server starts:**
  - an agent's image runs `server.ts`, generated by the plugin, which names only the task entry and the secrets;
  - `serve-<agent>` runs it with `docker run --env …`, by the agent image's tag (`plan.image`);
  - `AgentRuntime` sets its environment variables on AgentCore;
  - `integ/local/runtime` calls `startServer` with options;
  - `integ/aws/agentcore` builds an image that calls `startServer`, and deploys it with `AgentRuntime`.
- **Image identity:**
  - the `image` executor writes each layer's id with `--iidfile`, to `dist/<project>/image/agents/<agent>.id`;
  - an agent's construct builds `AgentRuntimeArtifact.fromAsset`, which CDK pushes to the assets repository tagged with the asset hash, its `extraHash` the parent image's id.
- **The records that call it open:** ADR 0008's mixed-version bullet and its 2026-09-29 amendment, and `docs/research/agentcore-runtime.md`'s note on sessions draining, each point to §ODO010.

## Goals / Non-Goals

**Goals:**
- One field on every task naming the image that ran it, set wherever the server starts, never defaulted.

**Non-Goals:** as in proposal.md.

## Decisions

### `image` is task metadata, stamped at admission

```ts
// core/agent-image.ts — shared by the server and the construct
export const AGENT_IMAGE_VARIABLE = 'AGENTFORGE_AGENT_IMAGE';

// server/runtime/server.ts
export interface ServerConfig {
  // …as today
  /** The image this server runs in: deployed, its container URI; locally, its image id. */
  readonly image: string;   // from the option, else AGENTFORGE_AGENT_IMAGE, required
}

// server/runtime/executor.ts and gateway.ts
export interface ExecutorConfig { /* …as today */ readonly image: string }
export interface GatewayConfig { /* …as today */ readonly image: string }
export function taskMetadata(envelope: Envelope, admission: Admission, image: string): Record<string, unknown>;
// { procedure, contractHash, idempotencyKey, runtimeSessionId, attempt, …, image, runs: [] }

// client/client.ts
interface TaskViewBase {
  readonly taskId: string;
  readonly contextId: string;
  readonly attempt: number;
  /** The image the task ran in (§REQ601). */
  readonly image: string;
  readonly runs: readonly RunRecord[];
}
```

- **One source.** As with the agent's name, whatever launches the server sets the value, the server's config holds it, and the server hands it to the executor and the gateway. Neither reads the environment.
- **Admission stamps it**, so a task keeps the image it was admitted under. A start that attaches to a task returns that task's metadata, never this container's image.
- **A start rejected for its size** carries it too, since `taskMetadata` takes it as a parameter at both call sites.
- **The wire schema requires `image`** as a non-empty string, so a client never reads a task without it.

*Alternative:* the task's `RunRecord`s. A run is recorded only once it settles, and a task may run no agent, so its image would be missing exactly where a crash leaves the most to explain.

### Where the value comes from

- **AgentCore:** `AgentRuntime` adds `AGENT_IMAGE_VARIABLE` to the variables it owns, and sets it to the container URI the L2 renders for the runtime's artifact. That is the same token CloudFormation passes as `AgentRuntimeArtifact.ContainerConfiguration.ContainerUri`, set by property override as `AGENTFORGE_METRICS_RUNTIME_NAME` already is. The same value is `readonly image: string` on `AgentRuntime`.
  - The L2 binds the artifact while it renders. So the construct reads the rendered `ContainerUri` from the `CfnRuntime`, and throws at synth if it is absent, rather than leaving the variable unset.
  - The tag is CDK's asset hash, which changes with the agent's layer and, through `extraHash`, with every layer below it.
- **Locally:** `serve-<agent>` reads `dist/<project>/image/agents/<agent>.id`, its own input. It runs the container by that id rather than by tag, and passes `--env AGENTFORGE_AGENT_IMAGE=<id>`, so the recorded id is the image that ran even if the tag has moved since.
- **Integration:**
  - `integ/local/runtime` passes `image: 'runtime-integ'` and asserts it on a task;
  - the AgentCore fixture, deployed through `AgenticProjectResources` and `AgentRuntime` since `project-infrastructure`, gets it from the construct like any deployed agent.

## Error handling

| Failure | When | Outcome |
|---|---|---|
| `AGENTFORGE_AGENT_IMAGE` unset and no option given | server start | throws, naming the variable; the container never serves, so a deploy's readiness check fails it |
| The construct cannot read the runtime's container URI | synth | throws, naming the runtime |
| A consumer sets `AGENTFORGE_AGENT_IMAGE` in `environmentVariables` | synth | refused, as for every owned variable |
| `serve` without the agent's image id file | serve start | fails, naming the build that writes it, as the agent construct does for the parent image |
| A task without `image` read by the client | `GetTask` | the client throws: the task cannot be read; the wire rule in ARCHITECTURE §7 |

## What earns which test

- **Unit:**
  - `taskMetadata` with `image`;
  - the gateway: a start rejected for its size carries `image`;
  - the server's config refusing to start without it;
  - the client's `TaskView` carrying it, and refusing a task without it;
  - `AgentRuntime`'s `Template`: the variable is the artifact's container URI, and the owned variable is refused;
  - the serve executor's arguments: the run by id, and the variable.
- **Integration:** `integ` local's runtime suite asserts `image` on a task. The `aws` fixture deploys with it set.
- **e2e,** in the batch's joint verification (group 5):
  - `smoke-coverage` locally asserts `image` equals the id in its image file;
  - on AgentCore, it asserts `image` equals the stack's `HelloAgentImage` output, which is `AgentRuntime.image`.
- **Settled once:** that CDK's asset tag changes with the build context and `extraHash` is CDK's documented asset behaviour; it needs no test.

## Risks / Trade-offs

- [A tag is not a digest: a tag pushed again could name different bytes] → CDK names the tag by the asset's content hash, so the same tag is only ever pushed for the same build inputs. A consumer that needs the exact digest resolves it from the registry by the tag.
- [**BREAKING** on the wire] → The wire rule `strict-contracts` records in ARCHITECTURE §7: versioned with the package, taken by a project and its callers in one deploy, and no consumer is live.
